## Causa A: la versión 27 no está declarada fuera de TypeScript

- **Síntomas.** `openclaw-database-preflight`: `expected { state: 19, agent: 24 } to deeply equal { state: 27, agent: 24 }`
  (`package.json` `openclaw.schemaVersions.state: 19` frente a `OPENCLAW_STATE_SCHEMA_VERSION` 27).
  `check-native-state-schema-version`: `Native state schema version drift: Swift supports 19, TypeScript owns 27`.
  `update-command-admit`: `state database … has schema 27; target supports 19`.
- **Causa.** B0→B3 subieron el esquema de estado a 27 sin alinear `package.json` ni la constante Swift
  `maximumSupportedSchemaVersion` (`apps/shared/OpenClawKit/Sources/OpenClawNativeState/OpenClawNativeStateSQLite.swift:43`).
  El "target supports 19" de la admisión de updates sale del mismo `package.json` vía `supportedVersions`
  (`src/cli/update-cli/schema-preflight.ts:57`, alimentado por `preflightOpenClawDatabaseSchemas`); no hay segundo punto.
- **Lectura de Swift antes de subir el número.** Líneas 296-300: el guard rechaza bases con `user_version` mayor que el
  máximo (con 19 rechaza una 27; con 27 pasa). 302-318: la lista cerrada de `validateVersionZeroOwnership` (433-463)
  solo corre con `user_version == 0` (línea 302), así que no cuenta; una base versionada entra por 312-318:
  `validateSharedDatabaseMetadata` (465-480, valida `schema_meta` contra la versión) y existencia de la tabla nativa
  pedida (314-318). `validateTableShape` (482-498) valida columnas, STRICT e índice de solo esa tabla. El diff no toca
  ninguna tabla nativa, así que subir a 27 no rompe ninguna validación.
- **Arreglo.** `package.json` `state` 19→27 (`agent` queda 24) y Swift `maximumSupportedSchemaVersion` 19→27.
- **Rojo** (`rojo.log`): las 3 pruebas.
- **Mutaciones.** `mutacion-A.log`: `package.json` de vuelta a 19 → preflight rojo
  (`expected { state: 19, agent: 24 } to deeply equal { state: 27, agent: 24 }`, 1 failed | 21 passed).

## Causa B: tres columnas de la v25 registradas como aditivas de la misma versión

- **Síntomas.** `openclaw-database-maintenance.test.ts:170` y las 2 de `read-only-state-compat.test.ts:41-58`:
  `error in index idx_managed_tasks_projection_pending after drop column: no such column: projection_json`.
- **Causa.** `412bf5be195` ("Add durable managed task progress projections") creó `managed_tasks.projection_json`,
  `projection_receipt_json` y `projection_publisher_host_id`, su índice parcial (`openclaw-state-schema.sql:1614-1616`),
  subió a v25 y además registró las tres en `lazyColumns` (`src/state/openclaw-state-db-additive-columns.ts:48-50`).
  Ese registro las declara como columnas que una base v25+ puede no tener, y es falso: las pruebas que recorren esa
  lista las borran con `DROP COLUMN` y el índice parcial revienta. Upstream registra así solo columnas opcionales; las
  que llegan con un salto de versión van en `versionedStateMigrations` (`src/state/openclaw-state-db-maintenance.ts`,
  v13→v18). La excepción upstream de v19 (`authorization_id` lazy con índice único) no se extiende a este índice:
  nuestras tres columnas son obligatorias en una base v25+.
- **Arreglo (sin tocar ninguna prueba).** Las tres columnas fuera de `lazyColumns`; nueva migración
  `migrateManagedTaskProgressProjections` con gate `previousVersion < 25`, que no hace nada si `managed_tasks` no
  existe (base nueva o `DROP TABLE`, `managed-task.store.test.ts:216`) y si existe agrega cada columna con
  `tableExists` + `ensureColumn` (estilo `migrateGitHubPublicationRequesterAuthority`, v18); entrada nueva al final de
  `versionedStateMigrations` con `applied: "Added managed task progress projection columns (v25)"`. Orden verificado en

  (:140-144) → `executeCanonicalStateSchema` (:147, crea `idx_managed_tasks_projection_pending`). Una base v24 termina

- **Rojo** (`rojo.log`): maintenance 1, read-only-compat 2.
- **Mutación** (`mutacion-B.log`): quitar la entrada de la migración → `managed-task.projection.test.ts` rojo
  ("upgrades a v24 task database and exposes legacy projection intent for reconciliation", 1 failed | 6 passed). Revertida.
