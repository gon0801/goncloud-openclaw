# Mac Terminal Control (David's Mac)

Drive Terminal.app and the macOS node via read-only `exec host=node` plus `osascript`, and resolve the permission-state confusion. Verified 2026-09-09 on node "David's MacBook Pro" (macOS 26.6.0, user `dn`).

## Steps

One command (`gh`, `ssh`, an installer) runs on the wrong machine when an exec omits `host="node"` on a Mac-targeted task (or vice versa): the failure is misleading (`gh: command not found` from `/bin/sh` on the gateway; a PowerShell parser error full of `-` tokens when bash script text is fed to Windows PowerShell). Rule: before any Mac-node exec, confirm the call carries `host="node" node="David's MacBook Pro"`; if you see PowerShell errors or wrong-OS paths in the output, the call ran on the gateway â€” re-run it on the node instead of debugging the command. For the node service's minimal PATH, source the profile or use absolute paths (`/opt/homebrew/bin/gh`) inside the same call. `background: true` without `host="node"` always lands on the gateway â€” background Mac jobs must carry the host parameters too, and their outcome can still be lost (`Node command outcome is unknown / COMPANION_APP_UNAVAILABLE` even when the work completed); verify effects with a read-only probe (files, `pgrep`) rather than rerunning blind.
   - Completion: shell output returns from the intended host (right OS, right paths).

2. List Terminal windows/tabs and their ttys with osascript:
   ```applescript
   tell application "Terminal"
     set out to ""
     repeat with i from 1 to count of windows
       repeat with j from 1 to count of tabs of window i
         set out to out & "win " & i & " tab " & j & " | tty=" & (tty of tab j of window i) & " | title=" & (custom title of tab j of window i) & linefeed
       end repeat
     end repeat
     return out
   end tell
   ```
   This yields the `win â†’ tab â†’ tty â†’ title` map (e.g. `win 1 tab 1 | tty=/dev/ttys005 | title=â€¦`). Cross-reference `ps -o pid,tty,stat,command -p <pid>` to know which tab hosts which process.
   - Completion: you have the tabâ†’ttyâ†’title map and know which tty each agent process lives on.

3. Select the target tab by its **tty**, resolving the window in the same script â€” never by a window index you captured earlier (see Pitfalls):
   ```applescript
   tell application "Terminal"
     repeat with i from 1 to count of windows
       repeat with j from 1 to count of tabs of window i
         if (tty of tab j of window i) is "/dev/ttysNNN" then
           set index of window i to 1
           activate
           set selected of tab j of window 1 to true
         end if
       end repeat
     end repeat
   end tell
   ```
   - Completion: the target tab is selected without an AppleScript error, and reading back `contents of tab 1 of window 1` shows the expected session.

4. **Check `mac-tmux-control` first.** David launches CLI agents with `~/bin/agent-tmux.sh`, so if `/opt/homebrew/bin/tmux list-sessions` shows the target session, type there by session name and skip the keystrokes below; they are only for a tab that is genuinely outside tmux. Never write to `/dev/ttysNNN` as "input": on macOS a tty device write is output painted on the screen (no TIOCSTI), so the text looks typed while the program received nothing (2026-09-14). Otherwise, type into the focused terminal:
   ```applescript
   tell application "System Events" to keystroke "<text>"
   tell application "System Events" to key code 36
   ```
   For a Claude Code TUI, delivering a task brief (verified 2026-09-13, v2.1.270): prefer Terminal's own `do script "<text>" in tab j of window i` â€” Terminal types the text and presses return. A SHORT string submits as a user message; a LONG one (a ~170-char `do script`, a direct TTY write `printf '<long text>' > /dev/ttysNNN`, a big clipboard paste, or 6-char chunks at typing speed) renders in the input box but is NOT submitted â€” the TUI reads the burst as paste and the trailing return inserts a line instead (a lone `\r` and extra Enter keystrokes did not submit either; the only submitted long input all day was a real cmd+V paste followed immediately by Enter, so treat that as unreliable). For a long brief: write it to a file on the Mac, then send one short `do script "Lee /tmp/brief.txt y haz lo que pide"`.
   - Verified 2026-09-14: a short `do script` delivered to a tab reference directly (`do script "..." in tab 1 of window 1`, index taken from the tab map built seconds earlier) submitted without first running the select/activate step of step 3, and the TUI accepted it as a user turn. Skip step 3 only when the index is fresh; re-resolve by tty on a stale map (Pitfalls: wrong-window delivery).
   - After repeated failed deliveries the input buffer corrupts (stacked unsubmitted lines; ESC and ctrl+U do not clear it). Recover by quitting the TUI (two ctrl+C written over the TTY) and relaunching it (`do script "claude"` in the same tab) â€” that cleared the wedge and the next short `do script` submitted.
   - A TUI survey option (e.g. Claude Code's "How is Claude doing this session? 1: Bad 2: Fine 3: Good 0: Dismiss") blocks the next delivery and leaves it queued: keystroke Enter or `0` via System Events did not register, but a SHORT `do script "0"` dismissed the survey AND submitted the queued brief (verified 2026-09-13, Claude Code v2.1.270). When a survey is on screen, dismiss it first, then confirm the real brief went through via the transcript/user-text marker.
   - Completion: `osascript` exits 0. Exit 0 only proves the keystroke was dispatched, NOT that a running TUI accepted it â€” a Claude Code transcript (`~/.claude/projects/<slug>/*.jsonl`) only advances when the turn commits, so mid-turn it shows nothing: read the live tab `contents` for a spinner/new turn instead (kimi-code: check the session log for a new `turnId`).
  - Synthetic Enter does not always submit a queued prompt, verified 2026-09-14 (codex TUI, window 34211: prompt text visible in the input line): repeated `System Events` key code 36 dispatched rc 0 with Terminal activated, yet the prompt sat unsubmitted through several rounds. Cap the synthetic-Enter retries at ~2. If a Mac-side agent is available (e.g. ingenieria), hand it the Enter instead of looping the same keystroke.
  - First rescue for a queued-but-unsubmitted prompt: an EMPTY `do script "" in tab j of window i` on the same tab submits it. Verified 2026-09-14 (muse-spark TUI, ttys005): a short `do script` left the brief prompt rendered in the input line, two `key code 36` rounds did nothing, then `do script ""` started the turn immediately ("Read /tmp/brief-f2-a4.md" + Thinking appeared). Cheaper than the tmux fallback below; confirm the turn started by reading back the tab.
  - **Reliable fallback: run the agent inside a tmux session you control** â€” verified 2026-09-14 on the same Mac/codex after keystroke failures: `/opt/homebrew/bin/brew install tmux` (if missing), `/opt/homebrew/bin/tmux new-session -d -s claw -c <repo-dir>`, launch the CLI inside (`/opt/homebrew/bin/tmux send-keys -t claw "codex" Enter`), then deliver prompts and confirmations with `/opt/homebrew/bin/tmux send-keys -t claw -l "<text>"` followed by `/opt/homebrew/bin/tmux send-keys -t claw Enter`, and read results with `/opt/homebrew/bin/tmux capture-pane -t claw -p`. send-keys is deterministic â€” it submitted a long question, a working turn, and a y-confirmation that synthetic Enter could not deliver. The session survives independent of Terminal focus; check `/opt/homebrew/bin/tmux ls` before reuse. Leave the session running as the standing control channel. Headless `/opt/homebrew/bin/codex exec` is NOT a substitute on repos whose hooks block runs (`hook: SessionStart Failed`, `hook: UserPromptSubmit Blocked`); never disable repo hooks to force it.
   - An all-black screenshot whose size/bytes are identical across recaptures means the display was asleep, not a capture failure — do not read it as permissions or a broken tool. Wake the screen and transfer the clean capture by the `mac-screenshot` procedure (wake first, size-check, scp via gonserver; never re-encode the image through a pipe).

For a long unattended run, poll the tab (~every 15 s) and send Enter when the prompt text appears, but do that polling from a **detached watcher**, not from one blocking call: start `nohup /tmp/watch-<name>.sh >/dev/null 2>&1 &` where the script reads the tab in a loop and exits (writing the last contents to a file) once the `esc to interrupt` status disappears; then poll that file with short reads. For a TUI that ends turns by delegating to its own background agents (Claude Code subagents), `esc to interrupt` disappears between turns while the overall task continues â€” poll for the specific expected OUTPUT marker instead (e.g. a line-start `VEREDICTO:`), and match it at line-start only: a marker that also appears inside the brief you pasted false-positives a plain tab grep (verified 2026-09-13, both cases). A detached watcher is the standard runner for long Mac waits â€” CI checks, TUI output, any remote loop â€” because one blocking exec risks the unknown-outcome loss (keep each exec call itself under ~30 s). Pattern, verified 2026-09-13 with a `/opt/homebrew/bin/gh pr checks` poll: write the script to `/tmp/watch-<name>.sh` on the Mac, `chmod +x` it, `nohup /tmp/watch-<name>.sh >/dev/null 2>&1 &` from a short exec, and confirm life in the SAME call with `ps aux | grep -v grep | grep watch-<name>` (a two-second `pgrep` right after launch can report the process dead before it exists). The script must end by writing its result to a status file â€” poll that file with short reads afterwards. A watcher that shells out to `gh` from an arbitrary cwd dies instantly with `fatal: not a git repository`; pass `-R <owner>/<repo>` (or `cd` inside the script) so it works from any launch directory. Relaunching after a failed exec needs the stale status file removed first â€” an old result at the same path reads as a fresh one.
   - Completion: the status file exists and carries a fresh result, or the process is alive in `ps` output.
   - Completion: the tab shows the run resumed (new output or a working spinner), the task is handed to a substitute agent open in the same project, or you have scheduled the resume for the reset time.

## Permission-state and reachability decision rules

- `nodes describe` `permissions.appleScript: false` can be **stale**. Re-run `nodes describe` after a reconnect before concluding the user must change System Settings; observed 2026-09-09 flipping to `true` with no System Settings change, after which `osascript` worked.
- `exec` running `osascript` may return `COMPANION_APP_UNAVAILABLE: macOS app exec host unreachable` while plain shell commands still succeed â€” this means the macOS app's automation/companion exec host is unreachable, not that the command is blocked. Retry after the app reconnects.
- To give a Claude Code tab a NEW task, type into its live tab (step 4). Do **not** try to drive that agent headlessly from `exec host=node`: `claude --print` / `claude -p` fails with `COMPANION_APP_UNAVAILABLE: macOS app exec host unreachable` (v2.1.269) because the CLI authenticates through the Claude desktop app's websocket, and neither `bash -l` nor a login shell supplies an `ANTHROPIC_API_KEY` to replace it. Opening a second, fresh Claude session hits the same wall. Read what the agent already said from its tab or its on-disk transcript (`mac-agent-transcript`), and extend the conversation by typing into the tab that is already open.
- `exec host=node` also fails with `... is not eligible; eligible node ids: <other>` when the macOS node itself is offline: confirm with `nodes status` (`connected: false`, `lastDisconnectedAtMs` set). This is a dropped node, not the companion app (shell commands fail too, unlike `COMPANION_APP_UNAVAILABLE`). Repeating the same call changes nothing until the node reconnects â€” report the blocker and let it return, rather than polling.
- On this Mac, node drops are local Wi-Fi flaps, not sleep: `pmset` shows `sleep 0` and no `Entering Sleep` entries; the log marks the drop with `swiftNetMon: reporting path update: unsatisfied (No network route), interface: en0[802.11]` followed by `Tailscale cannot connect because the network is down`, and recovery with a later `path update: satisfied`. The app itself survives (same pid). A caffeinate keepalive LaunchAgent (`~/Library/LaunchAgents/claw-openclaw-keepalive.plist`, runs every 300 s while OpenClaw.app lives; undo: `launchctl bootout gui/$(id -u)/claw-openclaw-keepalive` + remove the plist/script) is installed against idle-sleep. When a drop recurs, suspect the AP/router (or switch to Ethernet) â€” do not re-diagnose power settings. Verified 2026-09-13 (drop 02:48â€“06:15 PDT).
- Exactly ONE node process belongs on the Mac: the one OpenClaw.app spawns. A `launchd` job `ai.openclaw.node` (from `openclaw node` + `install`, or from accepting that offer in an interactive `openclaw doctor` on the Mac) dials `127.0.0.1:18789`, where nothing listens, and loops on `ECONNREFUSED` (2026-09-11 → 09-14, 11 000 failures, never paired). `openclaw node status` on the Mac must report no LaunchAgent; if it does, `openclaw node uninstall` — the app node is unaffected.
- **Computer use needs a vision-capable model** (it drives screen snapshots). A non-vision model (e.g. `deepseek-v4-pro`) cannot drive it even with `tools.alsoAllow: ["computer"]` set. For text-to-terminal tasks prefer `osascript`, which needs no vision.

## Pitfalls

- `osascript` tab selection: `set selected of tab N of window W to true` (not `set selected of window W to tab N â€¦`, which throws `-1700`).
- Reading a tab tail with an AppleScript range (`text -1600 thru -1 of contents`) throws "Invalid range" when the buffer is shorter than the range (verified 2026-09-13): return the full `contents` and cut client-side.
- **Window indices are not stable.** `set index of window i to 1` reorders windows, and macOS renumbers as tabs open/close. Reusing a window/tab index from an earlier map can silently select a *different* session â€” verified 2026-09-11, a paste meant for one Claude tab landed in another. Always resolve the window by its tty in the script that selects and types.
- A keystroke `exit 0` is not delivery confirmation into a TUI; confirm a new turn in the target agent's log before reporting success.
- The node exec sanitizes PATH and **`pathPrepend` is ignored**: every command carries `export PATH=/opt/homebrew/bin:/Users/dn/.local/bin:/Users/dn/bin:$PATH;` up front, or an absolute path. (This line previously asked only for `$PATH:/opt/homebrew/bin`, which left out `~/.local/bin` and `~/bin`, home of `pwsh`, `muse` and the `glm`/`deepseek`/`kimi-claude` launchers.) The node service PATH is minimal: homebrew CLIs are missing (`gh: command not found`). Prefer `/opt/homebrew/bin/gh ... -R <owner/repo>` so the call works from a non-repo cwd (otherwise: "fatal: not a git repository" â€” verified 2026-09-13, both).
- `/opt/homebrew/bin/gh pr checks` exits 8 while shards are pending (exit 8 â‰  failure); a CI watcher should loop on `grep -q pending` over its output and write the final summary to its status file, not parse the exit code (verified 2026-09-13, several polls).
